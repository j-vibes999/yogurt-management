# All-Swift Yogurt Manager Implementation Plan

> **For agentic workers:** Use subagent-driven-development for sequential implementation and task review. Continue within the owner's explicit migration authorization; do not ask to reauthorize the same scope.

**Goal:** Replace all remaining processing in the installed Mac application with Swift and ship a verified bundle using the existing Supabase database.

**Architecture:** Preserve the SwiftUI JSON-facing interface and durable operation store. Replace loopback HTTP with SwiftEngine calls, using PostgresNIO transactions and existing session/operation receipt formats. Retain legacy source as a test oracle only.

**Tech Stack:** Swift 6 toolchain (existing Swift 5 language mode), SwiftUI/AppKit, PostgresNIO, CryptoKit, CryptoSwift scrypt, existing PostgreSQL schema.

**Spec:** docs/superpowers/specs/2026-11-01-all-swift-design.md

## Global Constraints

- No production database mutations, migrations, seeds or synthetic data during verification.
- No installed-app cutover until parity tests pass. Never remove pending commands, drafts, receipts or backup evidence.
- Exact decimals and server-authoritative snapshots; no business arithmetic in Double.
- No JavaScript runtime, loopback HTTP listener or persistent helper in the final bundle.
- Existing Keychain service, project scope and private data paths remain compatible.
- Existing roles and revocable scrypt/session contracts remain authoritative.

## Review Focus

1. Lost commit replies retain the UUID/body and cannot become a second transaction.
2. Simultaneous payments and stock allocations preserve nonnegative stock/balances and audit-once behavior.
3. Session/role/password changes take effect for every current command and sensitive read.
4. Decimal boundaries/date cutoffs match the legacy oracle, including zero costs and fractional inventory.
5. Existing private receipts and drafts survive upgrade without becoming public or crossing accounts/projects.

### Task 1: Swift database, cryptography and exact-value foundation

Files: new Services/SwiftDatabase.swift, SwiftCredentials.swift, SwiftValue.swift and corresponding Swift tests; native/Package.swift and Package.resolved.
- [x] Add pinned/locked official PostgresNIO and CryptoSwift dependencies.
- [x] Implement the shared interfaces below using bound SQL, required certificate-verified TLS for Supabase, bounded pooling, cancellation and no raw connection errors.
- [x] Implement scrypt/HMAC session compatibility and exact decimal/date/canonical payload utilities; prove vectors generated by existing JS implementation.
- [x] Test local verification URL restriction and production TLS policy; never connect to production in unit tests. Reviewed clean through d04243b; 66 Swift tests pass.

Shared contract: `SwiftSQLConnection` is Sendable and offers `rows(_ sql:String, _ values:[JSONValue]) async throws -> [JSONValue]` for SELECT/WITH SELECT queries (each returned row is a JSON object with SQL column names, preserving Decimal), and `execute(_ sql:String, _ values:[JSONValue]) async throws`. `SwiftDatabase` offers the same reads and `transaction<T:Sendable>(_ work:@Sendable (SwiftSQLConnection) async throws -> T) async throws -> T`, plus async stop. Its initializer accepts BackendConfiguration and verification Bool; lifecycle is explicit. Values are positional PostgreSQL bindings ($1, etc.), with explicit casts where types require it; SQL never interpolates untrusted values. Transaction errors expose only safe SQLSTATE/code, not query/credentials.

`SwiftCredentials` exposes verifyPassword, session signing/verification and credential-tag helpers matching src/lib/password.ts and auth-session.ts. Keep random generation secure and constant-time comparisons. `SwiftValue` owns exact decimal parsing/rounding, JSON canonical hashing, safe IDs and UTC/Laos date helpers. Existing JSONValue/NativeSession are reused.
